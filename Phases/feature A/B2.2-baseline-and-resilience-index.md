# B2.2-baseline-and-resilience-index

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `B1.4` and `B2.1`, `findings/P0.1-findings.md`.

## Purpose

Turn ingested daily metrics into a personal 30-day baseline, deviation flags (|z| > 3) and the Personal Resilience Index, computed by a BullMQ worker that calls the FastAPI scoring service. Expose the results to the owner.

## What already exists

- Foundation files and P0 findings (chosen baseline rule, deviation rule, draft PRI formula).
- From `B1.1` to `B1.4`: API platform, DB and vaults, auth/consent/audit, BullMQ + `pending_jobs`, scoring client and FastAPI stubs.
- From `B2.1`: `wearable_daily`, ingest and demo endpoints, queue `ajna.wearable.compute-baseline` with no processor.
- No baselines, PRI or deviation tables.

## Scope

1. Worker processor for `ajna.wearable.compute-baseline`: load the subject's last 31 days (decrypt in the worker via the vault interface), call scoring, write results.
2. Real implementations in `services/scoring`: `POST /v1/score/baseline` (per-metric mean, SD or median/MAD per the P0.1 choice, valid-day counts) and `POST /v1/score/anomaly` (z-scores, deviation flags, PRI). Replace `stub-0` with `model_version: "pri-1.0"`.
3. Rules from `P0.1`: trailing window excludes the scored day, no flag before the minimum valid days, SD floor, no zero-filling of missing days.
4. Tables for baselines, daily PRI and deviation flags (Data model); these hold derived numbers keyed by `subject_id` (class 2 data).
5. Endpoints: `GET /v1/radar/summary` (latest PRI, trend, active deviation flags), `GET /v1/radar/pri?from&to`, `GET /v1/radar/deviations?from&to`.
6. Backfill: when a batch is ingested, process days in date order so baselines evolve as they would have in real time.
7. Recompute path: re-ingesting an earlier day triggers recomputation of that day and the following 30 days.
8. Respect `wearable` consent: revoking triggers the stub from `B1.4` to be filled here (delete derived radar rows for the subject within the retention rules).

## Out of scope

- Mobile UI (`M2.1`).
- Population aggregation of PRI (`B4.1`).
- Care-gap routing (`B4.2`).
- Any outreach or message to the user about a flag.

## Contracts used

Reads `openapi.v1.yaml` and `scoring.internal.v1.yaml`. Publishes `GET /v1/radar/summary`, `GET /v1/radar/pri`, `GET /v1/radar/deviations`; schemas `RadarSummary`, `PriPoint`, `DeviationFlag`. Updates `scoring.internal.v1.yaml` request/response schemas for baseline and anomaly.

## Data model

- `baselines(subject_id uuid, date date, metric text, mean numeric, sd numeric, median numeric null, mad numeric null, n_valid_days smallint, primary key(subject_id, date, metric))`
- `pri_daily(subject_id uuid, date date, pri smallint check (pri between 0 and 100), deviation_count smallint, model_version text, primary key(subject_id, date))`
- `deviation_flags(id uuid pk, subject_id uuid, date date, metric text, z numeric(5,2), direction text check (direction in ('high','low')), status text default 'flagged_for_review', model_version text)`
- RLS: owner read; worker write; no Official access to these row-level tables.

## Rules and behaviour

- A deviation flag is advisory. Its API field `status` is `flagged_for_review`; there are no `diagnosed` or `confirmed` values.
- No automatic message is sent about a flag. The owner sees it in the app; a Reviewer only sees it through population or care-gap flows built later.
- Metrics and z-scores never appear in logs. Job payloads contain ids only.
- Scoring requests contain numeric arrays and a request id only.
- Idempotent: re-running a job for the same day yields identical rows (upsert).
- If scoring is unavailable, state is `pending` and the endpoint returns the last good summary with `isStale: true`.

## Acceptance checks

- [ ] Unit tests in pytest reproduce the `P0.1` reference results on the shared synthetic dataset (report max absolute difference in z-scores: below 0.01).
- [ ] On the injected-event simulator set, detection rate and false flags per subject-month are within the `P0.1` numbers (report both).
- [ ] No flag appears before the minimum valid days (test over 20 new subjects).
- [ ] Idempotency and recompute tests pass (report counts of rows before/after).
- [ ] End to end: demo seed with `acute_deviation` produces the expected flags in under the `P0.1` time budget (report seconds from seed to summary).
- [ ] Throughput: 1,000 subjects computed; report jobs/sec and p95 and compare to `P0.1`.
- [ ] RLS: owner can read own radar rows, another user and Official cannot (report attempts).
- [ ] Consent revocation removes derived rows within the configured window (report timing).
- [ ] Wording lint over API strings and enums passes; grep for `diagnos` returns 0.
- [ ] Contracts regenerated; stale checks pass.
