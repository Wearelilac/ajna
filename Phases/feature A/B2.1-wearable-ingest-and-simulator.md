# B2.1-wearable-ingest-and-simulator

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `B1.1` to `B1.4`, `findings/P0.1-findings.md` (verdict `<verdict>`; canonical payload shape and limits).

## Purpose

Accept daily wearable metric summaries (real vendor-shaped payloads mapped to the canonical shape, or simulated), validate them, store them encrypted, and enqueue baseline computation. Also ship the simulator that makes the demo possible without a physical wearable.

## What already exists

- Foundation files and P0 findings.
- From `B1.1` to `B1.4`: NestJS API with errors, request IDs, logging and rate limiting; Postgres with roles and RLS; `VaultService` and `common/crypto`; auth, `@RequiresConsent`, `AuditService`; BullMQ worker, `pending_jobs`, scoring client; FastAPI scoring service stubs; contracts `openapi.v1.yaml` (health, ready, auth, me, consents, audit verify) and `scoring.internal.v1.yaml`.
- From `P0.1`: canonical payload shape, mapping rules, simulator design.
- No wearable tables or endpoints.

## Scope

1. Table `wearable_daily` with encrypted metric payload per row (see Data model).
2. Canonical payload validation (zod) with plausibility ranges per metric.
3. Vendor mappers for the payload shapes chosen in `P0.1` (Oura-style, generic), selected by a `source` field.
4. `POST /v1/wearable/daily` (single day) and `POST /v1/wearable/daily/batch` (up to 60 days), idempotent per `(subject_id, date, source)`; requires `wearable` consent.
5. Enqueue `ajna.wearable.compute-baseline` (id-only payload) after each accepted write; coalesce multiple writes for one subject within a short window into one job.
6. Simulator module (production-quality port of the P0.1 simulator): `POST /v1/wearable/demo-seed` creates 60 days of synthetic data for the calling user, with an optional `scenario` (`steady`, `gradual_decline`, `acute_deviation`); enabled only when `AJNA_ENV != production` or `AJNA_DEMO_MODE=true`.
7. `GET /v1/wearable/daily?from&to` returns the caller's own days, decrypted, so the app can show raw trends.
8. Audit rows for non-owner reads of wearable data (reviewer access is not part of this file, but the decorator is applied).

## Out of scope

- Baselines, z-scores, PRI, deviation flags (`B2.2`).
- Mobile screens (`M2.1`).
- Real vendor OAuth.
- Raw continuous sensor streams.

## Contracts used

Reads `openapi.v1.yaml`. Publishes into it: `POST /v1/wearable/daily`, `POST /v1/wearable/daily/batch`, `GET /v1/wearable/daily`, `POST /v1/wearable/demo-seed`; schemas `WearableDaily`, `WearableDailyInput`, `WearableSource`, `DemoScenario`. Adds error codes `WEARABLE_PAYLOAD_INVALID`, `WEARABLE_SOURCE_UNSUPPORTED`, `WEARABLE_BATCH_TOO_LARGE`, `DEMO_MODE_DISABLED`.

## Data model

- `wearable_daily(id uuid pk, subject_id uuid, date date, source text, ciphertext bytea, nonce bytea, dek_version smallint, received_at timestamptz, unique(subject_id, date, source))`
  - Plaintext canonical metrics (encrypted in `ciphertext`): `hrv_rmssd_ms`, `skin_temp_dev_c`, `resting_hr_bpm`, `sleep_total_min`, `sleep_deep_min`, `sleep_rem_min`, `sleep_light_min`, `sleep_awake_min`, `sleep_efficiency`, `activity_recovery_ratio`
- RLS: owner only; `app_worker` read for baseline jobs; `app_official` none.

## Rules and behaviour

- No metric values in logs, job payloads or error messages.
- Missing metrics are allowed (null), never zero-filled; at least one metric must be present.
- Dates cannot be in the future (UTC) or older than 13 months.
- Idempotency: resubmitting the same `(date, source)` replaces the row and re-enqueues.
- Respect `P0.1` limits (for example batch size, jobs per minute) from `common/limits.ts`.
- Wording: responses say "received"; no health interpretation here.
