# B4.1-population-aggregation-and-pgvector

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `B1.1` to `B1.4`, `B2.2`, `B3.1`, `findings/P0.3-findings.md` (verdict `<verdict>`, limits, chosen index and embedding features, query latencies).

## Purpose

Aggregate consented, de-identified signals into suppressed population views for public health officials: community risk trends, underserved-community clustering and similarity search, using Postgres and pgvector. Officials never see row-level data.

## What already exists

- Foundation files and P0 findings (P0.3 approach: HNSW/IVFFlat choice, embedding features, `K = 10` suppression via views).
- From `B1.x`: API platform, roles and RLS, vaults, auth/consent/audit, BullMQ and scoring service.
- From `B2.2`: `pri_daily`, `deviation_flags`. From `B3.1`: `deidentified_flags` (30-day retention) and crisis reviews.
- `subjects` already has nullable `age_band`, `region_code`, `community_id`.
- No population tables, views or endpoints.

## Scope

1. Tables: `communities`, `community_week_agg`, `community_month_agg`, `community_vectors` (pgvector), `community_clusters` (Data model).
2. Aggregation worker `ajna.population.aggregate` (scheduled daily and on demand): reads only subjects with active `population_use` consent, counts flags and PRI/deviation summaries per community, age band and week, writes aggregate rows. Aggregates keep **no `subject_id`**.
3. Retention interplay: when the 30-day flag retention job (from `B3.1`) deletes rows, aggregates computed from them are kept unchanged.
4. Suppression: all Official-facing views use `HAVING count(distinct subject_id) >= K` at aggregation time (store only counts above K; cells below K are stored as suppressed with no counts) with `K` from config (default 10). Complementary suppression to prevent subtracting totals to recover a small cell.
5. Community embedding builder: vector from normalised aggregate features (flag rate, mean PRI, deviation share, care-gap rate, deprivation index) per the P0.3 recipe; written to `community_vectors` with the chosen index.
6. Clustering job `ajna.population.cluster` (k-means or DBSCAN in the scoring service per P0.3) producing `underserved` groupings with a transparent score breakdown.
7. Endpoints for Officials and Admins: overview, community list with filters, community detail (trend lines), similar communities (pgvector nearest neighbours), cluster list.
8. Demo population seed: `POST /v1/admin/demo/population-seed` (non-production or demo mode) creating synthetic communities, subjects with coarse attributes, flags, PRI and care history for the dashboard demo (uses the P0.3 generator).
9. `app_official` role gets SELECT only on suppressed aggregate views; verify no grants on row-level tables.

## Out of scope

- Care-gap routing, pathways, drafts (`B4.2`).
- Dashboard UI (`W4.1`).
- Any individual-level output to Officials.
- Real demographic or deprivation data imports (synthetic or admin-provided values only).

## Contracts used

Reads `openapi.v1.yaml`. Publishes: `GET /v1/population/overview`, `GET /v1/population/communities`, `GET /v1/population/communities/{id}`, `GET /v1/population/communities/{id}/similar`, `GET /v1/population/clusters`, `POST /v1/admin/demo/population-seed`; schemas `PopulationOverview`, `CommunitySummary`, `CommunityTrend`, `ClusterSummary`, `SuppressedCell`. Error codes: `POPULATION_DATA_NOT_READY`.

## Data model

- `communities(community_id text pk, name text, region_code text, deprivation_index numeric(4,3) null, population_estimate int null)`
- `community_week_agg(community_id, week_start date, age_band text, subjects_n int, flag_count int null, mean_pri numeric(5,2) null, deviation_share numeric(4,3) null, suppressed boolean, primary key(community_id, week_start, age_band))`
- `community_month_agg(...)` same pattern
- `community_vectors(community_id pk, embedding vector(<N>), features jsonb, computed_at)` + `<HNSW|IVFFlat>` index
- `community_clusters(community_id, cluster_id int, label text, score numeric, score_breakdown jsonb, computed_at)`
- Views: `v_population_overview`, `v_community_summary` (suppression enforced)
- RLS/grants: `app_official` SELECT on views only; `app_worker` writes aggregates.

## Rules and behaviour

- Only `population_use`-consented subjects contribute. Revoking consent removes the subject from future aggregates; past aggregates contain no subject data.
- Suppressed cells return `suppressed: true` with null counts; the API never returns a count below `K`, nor a value computable from non-suppressed neighbours (complementary suppression test).
- Cluster labels are descriptive ("higher deviation share and lower PRI than peers"), never about individuals; the word `diagnos*` does not appear anywhere.
- Official-facing strings carry the advisory statement.
- If P0.3 was `limited-go`, enforce its row limits via config and expose a data-freshness field (`computedAt`).
- Performance targets from P0.3: overview and community queries under the 2-second target at the P0.3-supported row counts.

## Acceptance checks

- [ ] Seed 100k subjects (or the P0.3 limit); aggregation completes and reports runtime and rows written.
- [ ] Suppression test: attempt 20 queries designed to expose groups below K (filters, subtraction between totals and sub-groups); all return suppressed or total-only data (report 20 of 20).
- [ ] RLS: `app_official` cannot read any row-level table (list tables tried) and API role checks block `app_user` and unauthenticated calls.
- [ ] Consent: toggling `population_use` off removes the subject from the next aggregate (report counts before/after).
- [ ] Retention interplay: after the flag retention job runs, aggregate totals are unchanged (report numbers).
- [ ] Cluster recovery on seeded underserved communities: precision and recall within the P0.3 numbers (report both).
- [ ] Similar-community search: recall@10 versus exact search at least the P0.3 value (report).
- [ ] Endpoint latency at supported volume: p95 per endpoint under 2 seconds (report table).
- [ ] No `subject_id` column in any aggregate table (schema test).
- [ ] Contract regenerated and linted; stale check passes.
