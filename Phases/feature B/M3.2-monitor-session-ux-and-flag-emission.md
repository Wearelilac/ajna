# M3.2-monitor-session-ux-and-flag-emission

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `M1.2`, `M3.1` and `B3.1`, `findings/P0.2-findings.md`.

## Purpose

Build the user-facing Monitor Me experience: a consented, user-started, visible, time-capped session that runs the on-device engine and sends only the de-identified flags to the API. Foreground only.

## What already exists

- Foundation files and P0 findings.
- From `M1.1` and `M1.2`: app shell, auth, consent UI, Monitor Me tab (locked or unlocked by `monitor_me` consent), generated client.
- From `M3.1`: `src/edge` engine with `EdgeController` (`start`, `stop`, `status`, `onFlag`, required indicator callback), local `DeIdentifiedFlag` type.
- From `B3.1` (read via the contract): `POST /v1/monitor/sessions`, `POST /v1/monitor/sessions/{id}/end`, `POST /v1/monitor/flags`; schemas `MonitorSession`, `DeIdentifiedFlagInput`; error codes `FLAG_FIELD_NOT_ALLOWED`, `MONITOR_SESSION_REQUIRED`, `MONITOR_SESSION_EXPIRED`, `CONSENT_REQUIRED`.
- No session UI and no flag sending.

## Scope

1. Monitor Me home: privacy-first explainer (what is analysed, where, what is sent), consent state, and a large Start button.
2. Start flow: confirm dialog, request microphone permission, call `POST /v1/monitor/sessions`, then `EdgeController.start({ sessionId, maxDurationSec })` with the server-provided cap.
3. Visible listening indicator: persistent in-app banner with elapsed and remaining time and a prominent Stop button; a platform foreground notification or status indicator if `P0.2` found it necessary and permitted.
4. Flag emission: the single bridge between `edge` and the network lives in `src/features/monitor/flagSender.ts` (outside `src/edge/`). It receives `onFlag`, validates the object against the generated `DeIdentifiedFlagInput` type, and calls `POST /v1/monitor/flags`.
5. Offline handling: queue flag objects only (allow-listed fields) in memory with a small cap (for example 20); resend on reconnect; drop on session end or sign-out. Never queue audio or features.
6. Stop paths: user stop, cap reached, backgrounded, interruption, consent revoked, sign-out; each ends the engine, then calls `POST /v1/monitor/sessions/{id}/end` with a reason.
7. Post-session summary: duration and number of flags sent, "Nothing was recorded or saved on your phone", and a link to privacy settings. No flag contents are shown beyond counts.
8. Safety information: a static, always available "If you are in crisis" panel with local helpline information supplied as static content (configurable per region) and clear wording that Ajna does not contact emergency services or anyone on the user's behalf.
9. App-side proof hooks: a debug-only screen (dev builds) showing engine counters and a "last outbound request size" meter, to support demos of the privacy claim.

## Out of scope

- Engine internals (`M3.1`).
- Server logic (`B3.1`) and staff review (`W3.1`).
- Notifications to users about reviews or outcomes.
- Background or locked-screen listening beyond `P0.2` limits.

## Contracts used

Reads only: `/v1/monitor/sessions`, `/v1/monitor/sessions/{id}/end`, `/v1/monitor/flags` and schemas listed above. Publishes nothing.

## Data model

Client-side:

- `useMonitorStore { status: 'idle'|'starting'|'listening'|'stopping'|'error', sessionId?, startedAt?, maxDurationSec?, flagsSent: number, queueLength: number }`
- In-memory `flagQueue: DeIdentifiedFlag[]` (cap 20, never persisted)
- No health or audio data stored.

## Rules and behaviour

- Starting requires active `monitor_me` consent (checked locally and enforced by the server).
- The session cannot start silently: the indicator is shown before the engine starts, and the engine refuses to run without its indicator callback.
- Sessions are capped (server value) and end automatically.
- The only network traffic from this feature is: session start, flag post(s), session end. No audio-sized payloads. A test measures this.
- Wording: "an advisory signal may be shared for human review", never "we detected abuse/distress/condition". No promises of intervention.
- Revoking consent ends any running session immediately.

## Acceptance checks

- [ ] Start, run, stop on a named Android device and a named iPhone against the deployed API (report session ids and results).
- [ ] The listening indicator is visible within 300 ms before engine start in all start tests (report measured timing).
- [ ] Cap test: server `maxDurationSec` reached, session ends automatically, engine stopped, mic released (report timings).
- [ ] Network audit during a 10-minute session with no threshold crossing: only session start and session end requests exist, none larger than the contract allows (report request list and sizes).
- [ ] Injected 5 threshold crossings: exactly 5 `POST /v1/monitor/flags` calls, each payload equals the allow-list fields only (show captured payloads, redacted ids).
- [ ] Offline test: flags queue (cap 20), resend on reconnect, queue is cleared on session end/sign-out; the queue contains no field outside the allow-list (report test names).
- [ ] Interrupt tests: background, call, consent revoke, sign-out, each ends the session cleanly (report 4 cases).
- [ ] Rejected-field test: tampered flag object with an extra field is blocked client-side and, if sent, rejected server-side (report both).
- [ ] Wording lint: 0 banned words; crisis panel present and static.
- [ ] Re-run `M3.1` canary test inside the full app flow: pattern absent from storage, logs and requests (report what was scanned).
