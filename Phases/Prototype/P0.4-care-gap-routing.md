# P0.4-care-gap-routing

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `P0.1`, `P0.2` and `P0.3`.

## Purpose

Throwaway experiment answering: can Ajna map an elevated risk score or an overdue screening to an **approved** care pathway using pgvector, generate a tailored outreach **draft**, and run it through a human staff review workflow, with no automatic sending and no diagnostic language? Output is a findings note. `B4.2` and `W4.2` must not start until it exists.

## What already exists

- Foundation files, and findings notes from `P0.1`, `P0.2`, `P0.3` (including the pgvector setup and synthetic population).
- No production tables, endpoints, screens or jobs.

## Scope

1. **Approved pathway library.** Write 15-25 synthetic `care_pathways` entries (Well-Child Visit by age band, adult comprehensive screening, immunisation catch-up, stress and sleep support programme, community mental health contact, nutrition and activity programme). Each has: id, title, eligibility rules (age band, indicator type), plain-language description, approved wording snippets, owner role, and an `approved_by` and `approved_on` field. The system may only choose from this list.
2. **Risk to pathway mapping.** For each subject-level or community-level indicator (deviation flag pattern, low PRI trend, overdue screening, de-identified flag count in a review window), build a text or feature embedding and retrieve the top-k pathways via pgvector. Apply hard eligibility filters first (age band, indicator type), then vector similarity. Evaluate on a labelled set of 200 synthetic cases made by a reviewer: top-1 and top-3 accuracy, and "no suitable pathway" handling.
3. **Overdue detection.** Query for overdue Well-Child Visits and adult screenings from `care_history` and the schedule in `care_pathways`.
4. **Outreach draft generation.** Template-driven drafts filled with approved wording snippets, optionally polished by an LLM call constrained to the snippets (record whether an LLM is used and flag it under Gaps found if so, since the locked stack has none). Drafts must be tailored (language level, age band, tone) and must pass the banned-wording lint from `00-data-protection-model.md` section 8.
5. **Staff review workflow.** Prototype the state machine: `draft` → `in_review` → `approved` | `edited_approved` | `rejected` → `closed`. Record reviewer, timestamp and reason on each transition. Approval only records a decision: it does not send anything.
6. **Safety checks.** Verify there is no code path that sends a message, and that a draft cannot reach `approved` without a Reviewer role action.
7. **Findings note** at `findings/P0.4-findings.md`.

## Out of scope

- Real SMS, email or letter delivery, in this file and in the whole prototype.
- Production schema, endpoints and UI (`B4.2`, `W4.2`).
- Crisis review (`B3.1`, `W3.1`), though the state machine pattern here is reused there.
- Clinical content authoring. Pathways are synthetic placeholders to be replaced by a clinical owner.

## Contracts used

None.

## Data model

Prototype tables in `prototypes/p0.4/`:

- `care_pathways(id, title, eligibility jsonb, description, wording_snippets jsonb, owner_role, approved_by, approved_on, embedding vector(N))`
- `care_gaps(id, subject_id, gap_type, due_date, indicator_summary jsonb, created_at)`
- `pathway_matches(care_gap_id, pathway_id, rank, similarity, filtered_by jsonb)`
- `outreach_drafts(id, care_gap_id, pathway_id, body, language, status, generated_by, created_at)`
- `draft_reviews(id, draft_id, reviewer_id, from_status, to_status, reason, edited_body, at)`

## Rules and behaviour

- Approved pathways only. If no pathway passes the eligibility filters and a similarity threshold, the case is `no_suitable_pathway` and goes to a human.
- Draft wording: "may benefit from", "is due for", "we would like to offer". Never "diagnosed", never "we detected", never reveal that audio or flags led to the message.
- Drafts do not include sensitive signal details (no mention of distress signatures or specific metrics).
- Every draft carries `status = draft` until a Reviewer acts. There is no auto-approve and no timer-based approval.
- Every transition is audit logged (use a simple hash-chained table here, to practise the pattern for `B1.3`).
- If an LLM is used it receives only the pathway snippets and age band, with no identifiers.

## Acceptance checks

- [ ] 15-25 pathways entered; each has `approved_by` and `approved_on`.
- [ ] Mapping evaluated on 200 labelled cases: report top-1 accuracy, top-3 accuracy and the `no_suitable_pathway` rate.
- [ ] Eligibility filters verified: a test shows a pathway outside the age band is never returned even if most similar.
- [ ] Overdue detection correct on a seeded set (report seeded vs found counts for Well-Child Visits and adult screenings).
- [ ] 100 drafts generated; banned-wording lint passes on all 100 (report violations: expected 0).
- [ ] Review state machine tested: all legal transitions pass, all illegal ones (for example `draft` → `approved`) fail with an error (report the transition matrix).
- [ ] Static check: no import or call to any messaging provider anywhere in `prototypes/p0.4/` (show the grep).
- [ ] Draft generation time per draft (median ms) and, if an LLM is used, the cost estimate per 1,000 drafts.
- [ ] Verdict `go`, `limited-go` or `no-go` in `findings/P0.4-findings.md`, with limits quoted.
