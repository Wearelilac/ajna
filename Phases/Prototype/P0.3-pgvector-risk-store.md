# P0.3-pgvector-risk-store

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoffs of `P0.1` and `P0.2`.

## Purpose

Throwaway experiment answering: can Render PostgreSQL with pgvector store de-identified flags and PRI summaries, answer population aggregation queries, and support similarity and clustering for "underserved community" views at realistic row counts, with RLS and small-cell suppression, within dashboard-friendly latency? Output is a findings note. `B4.1` and `W4.1` must not start until it exists.

## What already exists

- Foundation files, and the findings notes of `P0.1` and `P0.2` (for the flag shape and the PRI draft).
- No production tables, endpoints, screens or jobs.

## Scope

1. **Provision** a Render PostgreSQL instance (free or lowest tier) with `pgvector` enabled. Record the version, tier limits (storage, connections) and extension availability.
2. **Synthetic population.** Generate 100,000 subjects (also test 10,000 and 1,000,000 rows of flags) with: pseudonymous `subject_id`, age band, region code (about 200 synthetic communities), a synthetic deprivation index per community, daily PRI summaries, de-identified flags following the allow-list in `00-data-protection-model.md`, and last-visit dates for Well-Child Visits and adult screenings.
3. **Tables and indexes.** Create prototype tables for flags, PRI summaries, subjects (coarse attributes only) and `community_vectors(community_id, embedding vector(N))`. Try HNSW and IVFFlat indexes and compare.
4. **Aggregation queries.** Write and time: flags per community per week, mean PRI per community per month, share of subjects with deviation flags, overdue-screening counts per community and age band. Apply small-cell suppression (`K = 10`) inside a view, so rows below K are never returned.
5. **Similarity and clustering.** Build a community embedding (for example: normalised vector of flag rates, mean PRI, care-gap rates, deprivation index). Use pgvector nearest-neighbour search to answer "communities most similar to X" and k-means or DBSCAN (run in the scoring service environment, written back) to produce an "underserved community" grouping. Check on the synthetic ground truth that planted underserved clusters are recovered (report precision and recall).
6. **RLS check.** Enable and force RLS on the row-level tables, create `app_official` with no policy on them but SELECT on the suppressed views, and verify the Official role cannot read row-level data by any query attempted.
7. **Retention check.** Run the 30-day flag retention job on the prototype: delete rows, count into aggregates, confirm aggregates are unchanged by the deletion.
8. **Findings note** at `findings/P0.3-findings.md`.

## Out of scope

- The real aggregation worker and API (`B4.1`).
- The dashboard UI (`W4.1`).
- Care pathway mapping and outreach (`P0.4`, `B4.2`).

None.

## Data model

Prototype tables in `prototypes/p0.3/`:

- `subjects(subject_id uuid pk, age_band text, region_code text, community_id text)`
- `deidentified_flags(id uuid pk, subject_id uuid, signature text, confidence numeric(3,2), time_bucket timestamptz, model_version text, session_id uuid)`
- `pri_daily(subject_id uuid, date date, pri smallint, deviation_count smallint, primary key (subject_id, date))`
- `care_history(subject_id uuid, service_type text, last_done date, due_date date)`
- `community_vectors(community_id text pk, embedding vector(16), cluster_label text)`
- Views: `v_community_weekly_flags`, `v_community_pri`, `v_care_gap_counts` (all with `HAVING count(distinct subject_id) >= 10`)

## Rules and behaviour

- Only synthetic data. No real health data enters this experiment.
- Population views never return a group below `K = 10` subjects.
- Official role: no direct table access.
- Embeddings are built from aggregates, never from individual subjects, so a community vector cannot reveal an individual.
- Queries are measured with `EXPLAIN (ANALYZE, BUFFERS)` and warm cache, repeated 5 times, report the median and worst.
- Wording in any view or column comments follows the glossary ("flagged", never "diagnosed").

## Acceptance checks

- [ ] pgvector version and Render tier limits recorded.
- [ ] Row counts loaded: 1k / 10k / 100k / 1M flags (report load time for each).
- [ ] Each aggregation query timed at each row count (median and worst ms) and a verdict stated against a 2-second dashboard target.
- [ ] HNSW versus IVFFlat: build time, index size (MB), query ms and recall@10 against exact search.
- [ ] Cluster recovery on planted underserved communities: precision and recall reported.
- [ ] Small-cell test: attempted queries returning groups with fewer than 10 subjects return zero such rows (show the test).
- [ ] RLS test: `app_official` attempts SELECT on every row-level table and every attempt fails (list tables).
- [ ] Retention job test: flag rows older than 30 days deleted, aggregate totals unchanged (show before/after numbers).
- [ ] Storage used at 1M flags (MB) and whether it fits the free/low tier.
- [ ] Verdict `go`, `limited-go` or `no-go` recorded in `findings/P0.3-findings.md`, with limits (for example "tier supports up to 100k subjects, not 1M").
