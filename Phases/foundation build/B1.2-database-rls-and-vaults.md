# B1.2-database-rls-and-vaults

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, handoff of `B1.1`, `findings/P0.3-findings.md`.

## Purpose

Stand up the production Postgres schema foundation: migrations, roles, Row-Level Security, pseudonymous IDs, the AES-256-GCM envelope-encrypted vault, and the crypto module. Later files add tables on top of this pattern.

## What already exists

- Foundation files and P0 findings.
- From `B1.1`: `apps/api` skeleton, env validation, `AppError`, request IDs, pino logging, `common/limits.ts`, `contracts/openapi.v1.yaml` v1 (health, ready, ErrorResponse, bearerAuth).
- No tables, roles, vaults or crypto module.

## Scope

1. Choose and set up a migration tool (for example `node-pg-migrate` or Drizzle migrations; flag under Gaps found if outside the stack) and a `db/migrations` folder.
2. Enable extensions: `pgcrypto`, `vector`.
3. Create DB roles: `app_user`, `app_reviewer`, `app_official`, `app_worker`, `app_admin`, with least-privilege grants.
4. Create core tables (below) with `ENABLE` and `FORCE ROW LEVEL SECURITY` and policies per `00-data-protection-model.md` section 7.
5. `common/crypto` module: AES-256-GCM encrypt/decrypt with per-field nonces and `subject_id` as AAD; DEK generation; DEK wrap/unwrap with the KEK from env; KEK re-wrap script.
6. Vault service: `VaultService.put(subjectId, key, plaintextJson)` and `get(...)`, storing only ciphertext, nonce and key version.
7. DB access layer that opens a transaction, sets `app.subject_id` and `app.role` with `SET LOCAL`, and runs queries as the matching role.
8. Seed script producing 20 synthetic subjects.
9. Wire `GET /v1/ready` to check database connectivity.

## Out of scope

- Auth and consent logic (`B1.3`).
- Audit chain (`B1.3`).
- Wearable, flag, review and care tables (`B2.1`, `B3.1`, `B4.x`).
- Queues (`B1.4`).

## Contracts used

Reads `openapi.v1.yaml` v1. Publishes no new endpoints (`GET /v1/ready` gains a `database` field in its response schema).

## Data model

- `subjects(subject_id uuid pk default gen_random_uuid(), created_at, age_band text null, region_code text null, community_id text null, deleted_at timestamptz null)`
- `vaults(subject_id uuid pk references subjects, wrapped_dek bytea, dek_nonce bytea, kek_version smallint, created_at)`
- `vault_items(id uuid pk, subject_id uuid, item_key text, ciphertext bytea, nonce bytea, dek_version smallint, created_at, unique(subject_id, item_key))`
- `schema_migrations` (tool managed)

RLS: `subjects`, `vaults`, `vault_items` allow rows where `subject_id = current_setting('app.subject_id')::uuid` for `app_user`; `app_worker` has narrow explicit grants; `app_official` has no policy.

## Rules and behaviour

- Nonces are random 96-bit and never reused with the same DEK (test generates 100,000 nonces and asserts no collision).
- Decryption failure returns a generic `VAULT_DECRYPT_FAILED` error and logs the code and `requestId` only.
- No plaintext PHI column exists anywhere. A schema test lists columns of every table and fails on names like `name`, `email`, `phone` outside the vault.
- KEK access is isolated in `common/crypto`; nothing else reads `AJNA_KEK_BASE64`.
- If P0.3 returned `limited-go`, size assumptions in comments reference its limits.

## Acceptance checks

- [ ] Migrations run up and down cleanly on an empty database (report both exit codes).
- [ ] RLS matrix test: for each new table and each of 5 roles and each of SELECT/INSERT/UPDATE/DELETE, actual versus expected results (report the matrix and mismatches: 0 expected).
- [ ] Cross-subject test: subject A cannot read or update subject B's vault rows (report the attempted operations).
- [ ] Round trip: encrypt/decrypt 1,000 random JSON payloads, all equal; tampering one byte of ciphertext or AAD fails (report counts).
- [ ] Nonce uniqueness test passes at 100,000 samples.
- [ ] KEK rotation script re-wraps all DEKs for the 20 seed subjects and all vault items still decrypt (report counts).
- [ ] Schema test finds no plaintext PHI-named columns.
- [ ] `GET /v1/ready` reports database status and the contract is regenerated.
- [ ] Encrypt/decrypt cost: median ms per 1 KB item (report).
