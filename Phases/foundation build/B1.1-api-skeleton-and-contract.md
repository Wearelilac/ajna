# B1.1-api-skeleton-and-contract

**Read first:** `00-glossary.md`, `00-stack-and-conventions.md`, `00-data-protection-model.md`, `00-system-map.md`, and the findings notes `findings/P0.1` to `P0.4` (read the verdicts and limits; the P0 handoff blocks feed this file).

## Purpose

Create the NestJS API skeleton that every later backend file builds on: project structure, env validation, the standard error shape, request IDs, structured logging, health endpoints and the first version of `contracts/openapi.v1.yaml`. Clients (`M1.1`, `W1.1`) start from this contract in parallel.

## What already exists

- Foundation files and P0 findings notes only (verdicts: P0.1 `<verdict>`, P0.2 `<verdict>`, P0.3 `<verdict>`, P0.4 `<verdict>`).
- Throwaway code in `prototypes/` (never imported).
- No production code, tables, endpoints, screens or jobs.

## Scope

1. Create `apps/api` (NestJS, Fastify adapter, TypeScript strict) with the layout in `00-stack-and-conventions.md`.
2. Env validation module (zod): refuse to boot on missing or malformed variables, print names only. Commit `.env.example`.
3. Global exception filter producing exactly `{ statusCode, error, code, message, requestId }`. Define an `AppError` class with stable `code` values and a registry file listing all codes.
4. Request ID middleware: accept a valid `x-request-id` or generate a UUID, attach to logs and the response header.
5. Structured logger (pino) with redaction rules from the logging section of the conventions file.
6. OpenAPI generation via `@nestjs/swagger` with zod DTOs (`nestjs-zod`); an npm script writes `contracts/openapi.v1.yaml` and a CI script fails if the committed file is stale.
7. Endpoints: `GET /v1/health` (liveness) and `GET /v1/ready` (checks DB and Redis connectivity once those exist; return `degraded` flags, never crash).
8. Rate limiting (Fastify rate-limit plugin) with sane defaults and per-route override support.
9. Render deployment config (`render.yaml` entry for the web service) and a CI workflow running lint, type check, tests and contract check.

## Out of scope

- Database, migrations, RLS, vaults (`B1.2`).
- Auth, consent, audit (`B1.3`).
- Queues, workers and the scoring service (`B1.4`).
- Any feature endpoint.

## Contracts used

Publishes to `contracts/openapi.v1.yaml`: `GET /v1/health`, `GET /v1/ready`, the shared `ErrorResponse` schema and the shared `bearerAuth` security scheme (declared now, used from `B1.3`).

## Data model

None. No tables yet.

## Rules and behaviour

- Every error path, including 404, validation failures and rate limits, returns the standard error shape.
- Validation failures use codes like `VALIDATION_FAILED` with a safe `message`; never echo request bodies.
- No PHI or secrets in logs. A test posts a request containing fake PHI and fake token strings and asserts they do not appear in captured log output.
- Controllers contain no business logic; services do. Modules follow `modules/<feature>/`.
- If P0.1 or P0.3 returned `limited-go`, record the limits as config constants in `common/limits.ts` for later files to read.

## Acceptance checks

- [ ] `npm run build` and `npm test` pass; report test count and coverage percentage.
- [ ] Booting with a missing required env var exits non-zero and prints the variable name only (show the output with the value redacted).
- [ ] Hitting 10 different failing routes (404, bad body, wrong method, rate limit, etc.) all return the exact error shape; report the checked count.
- [ ] `x-request-id` round trip verified: supplied valid id is echoed, invalid id is replaced.
- [ ] Log redaction test passes (fake PHI and token never appear).
- [ ] `contracts/openapi.v1.yaml` generated, validates with an OpenAPI linter (report lint errors: 0 expected) and the CI stale-contract check fails when a route is changed without regenerating.
- [ ] `GET /v1/health` p95 latency under 50 ms locally over 200 requests (report the number).
- [ ] Deployed to Render and the health endpoint is reachable (report URL status and cold-start time).
